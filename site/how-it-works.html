How it works

The JohnArks Method is a build method for people who can't review code. You describe what you want in ordinary language; an AI agent builds it in small checkpoints. Every checkpoint passes five enforced quality gates, and every "done" is proven by a git commit plus a passing verification command — never by the agent's word.

The problems it solves

Each problem below is answered by a specific mechanism. Nothing here runs on trust.

"The agent said done. It wasn't."

AI agents hallucinate — confidently describing work they never did, tests they never ran, bugs they never fixed.

→ Done requires a real git commit, a verify command that exited 0, and an independent auditor that re-derives the outcome from the repo alone. A claim without evidence fails mechanically.

"I can't review code."

"Does this look right?" is not a question a non-developer can answer about code — so code review can't be your safety net.

→ You review the thing, not the code: touchable builds early, a vision-based UI reviewer comparing screenshots to the design, and a human gate presented in plain language.

"The session died / I switched tools."

Sessions run out of tokens. You move from Claude Code to Codex to whatever comes next — and all context evaporates.

→ Everything lives in the project's .jam/ directory and in git: product intent, plan, checkpoint state, decisions. One resume command picks up exactly where you left off, on any platform.

"I changed my mind mid-build."

You see a working build and realize you want something different. Most workflows either plow ahead or collapse.

→ Redirect is a first-class event: the loop stops, the agent asks focused questions about just the change, requirements and the decision log are updated, replaced checkpoints are marked superseded, and you approve the revised plan.

"Nobody remembers why we built it this way."

Months later, nobody knows which requirements drove which decisions — or which alternatives were rejected and why.

→ Product intent with stable requirement IDs, a decision log with reasons and rejected alternatives, and every checkpoint tracing to the requirements it satisfies.

"The agent wrote the record too."

If the same agent that did the work also writes the report, the report is just another claim.

→ A scribe records outcomes; a separate auditor with no access to the scribe's notes reconstructs them from git, files, and test evidence. Mismatch blocks progress.

How a build runs

  1. Discovery. The agent asks "What would you like to do?" — one focused question at a time. It writes requirements (FR-### / QR-###) and presents one product-intent summary. You confirm or correct it. Nothing is planned until you accept the summary.
  2. Planning. The work is split into small ordered checkpoints, each tracing to requirements and declaring its verify command. The plan front-loads something touchable — checkpoint 1 or 2 produces something you can open, click, and react to. You approve the sequence.
  3. Gated build loop. Each checkpoint runs: tests written first (they must fail), implementation, tests green — then the five gates below. A checkpoint is done only when all gates pass and the evidence is committed.
  4. Final review. A drift check diffs what was built against the product intent. You test as a user. Feedback becomes new checkpoints through the same loop.
  5. Redirect (any time). New idea, new feature, new direction? The loop stops, the delta is questioned and recorded, the plan is revised with your approval, and the loop resumes. Nothing built is lost.

The five gates

Every checkpoint passes through all five. The only allowed skip is the UI gate on purely logic-only checkpoints, with a recorded reason.

Gate 1 — Behavior

The checkpoint's declared verify command runs. Exit 0 means the behavior is proven, with the test report archived as evidence. Not "the agent says it works."

Gate 2 — UI review

A vision-based reviewer compares the implementation against the design reference in matching states, listing every difference with severity and location. Zero blockers to pass.

Gate 3 — Dual adversarial review

Two independent, context-isolated reviewers examine the code against the architecture doc. Both must approve. The builder fixes every finding and re-runs affected tests.

Gate 4 — Human review

You see what was built, the test results, and the reviewer verdicts — in plain language. Your approval, your feedback, your call.

Gate 5 — Independent audit

A scribe records the outcome; a separate auditor reconstructs it from git, files, and test evidence without seeing the scribe's notes. If they disagree, progress blocks until the record and reality match.

The trust chain

Every layer catches the layer above it. Any single liar is caught by the next.

The pieces

Seven skills, one enforcer, one hook, one installer. You only ever invoke one skill — the orchestrator runs the rest.

PieceWhat it does
orchestratorRuns the entire loop: discovery, planning, gated checkpoints, final review, redirect. The only skill you ever call on directly.
checkpoint-plannerSplits work into small ordered checkpoints, each tracing to requirement IDs with a declared verify command.
test-plannerDefines "proven": behavior test cases from your perspective, edges included, failing before the feature exists.
prototype-builderBuilds a clickable HTML prototype as the visual reference when no design exists yet.
ui-reviewerVision-based comparison of implementation vs. reference in matching states. Zero blockers to pass.
adversarial-reviewTwo isolated reviewers vs. the architecture doc. Both must approve.
design-plannerWrites the opinionated architecture/design doc the reviewers enforce.
jam.pyThe enforcer (stdlib Python, no dependencies). check validates state and evidence commits · resume prints the recovery brief · verify runs a checkpoint's verify command · gates reports open gates.
Stop hookClaude Code runs it on Stop: if the enforcer reports findings or gates are open, stopping is blocked until they're fixed. (Codex has no hook equivalent — the orchestrator runs the enforcer before every turn instead.)
install.shIdempotent installer: skills, enforcer, hook, routing block. Refuses to proceed on a non-git folder without your explicit decision.

The three prompts

Setup — new project

Set up the JohnArks Method in this project using https://github.com/johnarks/johnarksmethod. Install all skills and supporting files, wire up the quality gates, and confirm everything is working — if anything is already installed, confirm that instead of reinstalling it. If this folder is not a git repository yet, stop and ask me to create one before continuing. When setup is confirmed, ask me what I'd like to do.

Resume — new session, platform, or model

Resume the JohnArks Method in this project. Run python3 .jam/bin/jam.py resume, fix any findings it reports, then continue the build loop from the current checkpoint. Do not re-run discovery or re-ask settled questions.

Feedback / redirect — change your mind any time

I'm using the JohnArks Method in this project. I have feedback / new features / a direction change: <describe what you saw, what you want different, or the new direction> Pause the build loop. Ask me focused questions about anything unclear, then update the product requirements, checkpoint plan, and decision log to reflect this. Show me the revised plan for approval before continuing.

Who it's for

For: non-developers directing AI-built software; long-lived projects where sessions die and context must survive; people who switch between Claude Code, Codex, and future models; anyone burned by an agent that said "done" and wasn't.

Not for: trivial edits and one-off questions; teams with rigorous human code review on every change; anyone who wants the agent to "just do it" with no checkpoints — the method will fight you, by design.
